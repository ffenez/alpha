# Search UI / state fixes

## Цель

Привести экран `Поиск` к одному логичному состоянию без визуальных и логических противоречий.

Главное правило: **один источник истины для состояния поиска**. Нельзя отдельно вычислять текст статуса, видимость стрелки, доступность кнопки, карточку `Отпечаток места` и состояние `Проверка`.

Сейчас по скриншотам видно, что эти части живут независимо, поэтому одновременно появляются взаимоисключающие состояния:

- текущая скорость счёта уже приходит (`23,4–23,8 c⁻¹`);
- график обновляется;
- точка отсчёта уже сохранена;
- интерфейс всё ещё пишет `Ждём данные прибора`;
- в одном состоянии стрелка отсутствует;
- в другом стрелка появляется;
- после сохранения точки отсчёта интерфейс продолжает показывать текст, будто точка ещё не готова;
- `Отпечаток места` сообщает `мало данных`, хотя эталон уже накоплен несколько часов.

Это надо исправить на уровне state machine, а не отдельными `if` в UI.

---

# 1. Ввести единый SearchUiState

Сделать одно sealed-состояние, из которого рисуется весь экран.

Пример:

```kotlin
sealed interface SearchUiState {
    data object NoDevice : SearchUiState
    data object WaitingForLiveData : SearchUiState

    data class LiveNoReference(
        val cps: Double,
        val recentCps: Double?,
        val chart: List<Point>
    ) : SearchUiState

    data class ReferenceCollecting(
        val cps: Double,
        val reference: ReferenceSnapshot,
        val progress: ReferenceProgress,
        val chart: List<Point>
    ) : SearchUiState

    data class ReferenceReady(
        val cps: Double,
        val reference: ReferenceSnapshot,
        val ratio: Double,
        val interval: ClosedFloatingPointRange<Double>?,
        val verdict: SearchVerdict,
        val chart: List<Point>
    ) : SearchUiState
}
```

Названия можно адаптировать под текущую архитектуру, но смысл должен быть именно таким.

### Запрещено

Не должно быть отдельных флагов вида:

```kotlin
isWaiting
hasReference
showNeedMoreData
showNeedle
referenceReady
showGauge
```

которые обновляются независимо.

UI должен получать **одно непротиворечивое состояние**.

---

# 2. Исправить `Ждём данные прибора`

## Текущий баг

На экране отображается:

`Ждём данные прибора`

при этом:

- крупное CPS уже имеет живое значение;
- график строится;
- значит live-данные фактически поступают.

Это логически невозможно.

## Правильное условие

`Ждём данные прибора` показывать только если действительно нет валидного live measurement.

Например:

```kotlin
val hasLiveMeasurement =
    lastMeasurement != null &&
    now - lastMeasurement.timestamp < LIVE_TIMEOUT
```

Если `hasLiveMeasurement == true`, статус ожидания должен исчезнуть немедленно.

Не привязывать этот текст к:

- наличию профиля;
- наличию reference point;
- готовности fingerprint;
- длине history;
- спектру;
- обучению фона.

Это **только статус потока прибора**.

---

# 3. Стрелка должна определяться только наличием валидной точки отсчёта

Эталон поведения:

### Reference отсутствует

- дуга прибора видна;
- деления видны;
- стрелки нет;
- центральная точка допустима;
- подпись `отсчёт не задан`;
- CTA: `Запомнить текущий уровень`.

### Reference сохранён

Как только существует валидная точка отсчёта:

```kotlin
referenceCps > 0
```

и есть текущее CPS:

```kotlin
currentCps != null
```

должно вычисляться:

```kotlin
ratio = currentCps / referenceCps
```

и **стрелка должна быть видна всегда**.

Не ждать:

- статистической значимости;
- накопления окна;
- fingerprint;
- спектра;
- 15 минут;
- обучения профиля.

Эти данные нужны для уверенности в выводе, но не для самого положения стрелки.

---

# 4. Разделить `измеренное отношение` и `достоверность различия`

Сейчас UI смешивает две разные вещи.

Например:

`1,00× к точке отсчёта`

— это уже вычислимое отношение.

А:

`Разница пока не подтверждена`

— это статистический вывод.

Они могут существовать одновременно.

## Правильная модель

Всегда, когда reference есть:

```text
23,7 c⁻¹

1,00× к отсчёту
```

При наличии достаточной статистики ниже можно показать verdict:

```text
Без заметного изменения
```

или:

```text
Сигнал выше отсчёта
```

или:

```text
Сигнал ниже отсчёта
```

Если статистики мало:

```text
Пока недостаточно данных для уверенного вывода
```

Но **стрелка и отношение остаются**.

---

# 5. Убрать постоянный текст `Пока недостаточно данных`

Сейчас этот статус визуально слишком доминирует.

Он должен быть вторичным.

## Было

```text
● → Разница пока не подтверждена
1,00× к точке отсчёта 23,6 · оценочный интервал 0,72–1,35×
```

## Нужно

Основной слой:

```text
23,7
1,00× к отсчёту
```

Ниже одной короткой строкой:

```text
Недостаточно данных для уверенного вывода
```

А подробности:

- интервал;
- число измерений;
- метод;
- критерии;

перенести в `Почему?`.

На основном экране нельзя постоянно показывать статистическую методику.

---

# 6. Привести gauge к чистой геометрии

Сейчас есть несколько визуальных неровностей.

### Исправить:

- центральная ось `1×` должна попадать точно в геометрический центр дуги;
- label `1×` не должен пересекаться со стрелкой;
- стрелка не должна перекрывать текст;
- центральная точка должна быть точно на pivot;
- подписи `0,25× / 0,5× / 1× / 2× / 4×` должны лежать на одинаковом радиусе;
- `слабее / отсчёт / сильнее` — строго по одной baseline;
- дуга и active-fill должны иметь одинаковую толщину;
- interval-band не должен выглядеть как случайная вторая дуга;
- не использовать разные offsets для состояний `до отсчёта` и `после отсчёта`.

Gauge должен быть одним компонентом с одинаковой геометрией во всех состояниях.

---

# 7. Масштаб gauge

Оставить логарифмическую шкалу:

```text
0,25× — 0,5× — 1× — 2× — 4×
```

`1×` строго в центре.

Mapping:

```kotlin
val normalized =
    ((log2(ratio) + 2.0) / 4.0)
        .coerceIn(0.0, 1.0)
```

После этого переводить normalized position в угол дуги.

Не использовать линейное отношение для положения стрелки.

---

# 8. Поведение стрелки около 1×

Сейчас при `0,99×`, `1,00×`, `1,01×` стрелка визуально может казаться исчезнувшей или сливаться с центральной меткой.

Исправить.

Стрелка должна иметь:

- постоянную минимальную длину;
- толщину 2–3 dp;
- отдельный pivot;
- наконечник;
- контраст к background;
- z-index выше grid/interval band.

Даже при `ratio == 1.0` стрелка должна быть отчётливо видна вертикально вверх.

---

# 9. Не использовать зелёный цвет просто потому, что данные идут

На первом скриншоте `23,8` окрашено зелёным, хотя экран одновременно сообщает `Ждём данные прибора`.

Это ещё одно противоречие.

Цвет числа должен означать **состояние измерения**, а не случайный boolean.

Рекомендуется:

- neutral/ink — нет reference или вывод ещё не сформирован;
- green — измерение соответствует обычному уровню / нет значимого изменения;
- amber — заметное отклонение;
- red — превышение заданного критического порога.

Если данных недостаточно для классификации, число должно быть нейтральным, а не зелёным.

---

# 10. `Отпечаток места` — исправить логику готовности

На отдельном экране сейчас:

```text
Пока недостаточно измерений для сравнения с эталоном
```

при этом ниже:

```text
эталон создан ...
накопление 3,7 ч
спектр 59 мин
```

Это выглядит как баг состояния.

Нужно разделить три независимых readiness:

```kotlin
doseReady
countRateReady
spectrumReady
```

и общий verdict:

```kotlin
fingerprintReady =
    doseReady || countRateReady || spectrumReady
```

или другая научно обоснованная комбинация согласно текущему алгоритму.

Но нельзя показывать общий зелёный статус `недостаточно измерений`, если часть метрик уже готова.

## UI

Вместо:

```text
Мощность дозы       мало данных
Скорость счёта      мало данных
Форма спектра       мало данных
```

показывать реальное состояние каждой метрики:

```text
Мощность дозы        готово
Скорость счёта       готово
Форма спектра        собирается
```

Под каждой — только если нужны подробности:

```text
12 мин из 15
```

или:

```text
59 мин спектра
```

# 11. Убрать дублирование терминов `фон / отсчёт / эталон`

Сейчас одновременно существуют:

- фон;
- точка отсчёта;
- эталон;
- отпечаток места;
- недавний уровень.

Для пользователя это выглядит как пять похожих сущностей.

Нужно жёстко определить:

### Фон места
Долгосрочная статистика конкретного профиля/места.

### Точка отсчёта
Короткий reference для режима `Наведение`.

### Отпечаток места
Комплексное описание места: dose + CPS + spectrum.

### Недавний уровень
Только временная локальная baseline для графика, не сохранённая сущность.

После этого в UI не использовать эти слова взаимозаменяемо.

---

# 12. Наведение и Проверка должны быть разными задачами

## Наведение

Ответ на вопрос:

> Становится ли сигнал сильнее или слабее относительно выбранной точки?

Главный UI:

```text
CPS
↓
отношение
↓
gauge
↓
маленький live chart
```

## Проверка

Ответ на вопрос:

> Отличается ли текущее место/объект от сохранённого профиля?

Не нужно копировать UI Наведения.

В `Проверке` вместо полукруглого gauge лучше показывать компактный результат сравнения:

```text
Совпадает
```

или:

```text
Есть отличие
```

или:

```text
Данных пока мало
```

и ниже три составляющие:

```text
Доза       совпадает
CPS        совпадает
Спектр     собирается
```



# 19. Unit tests для state machine

Обязательно добавить:

### Live data пришли

```text
given currentCps exists
expect state != WaitingForLiveData
```

### Reference нет

```text
currentCps exists
reference == null

=> gauge visible
=> needle hidden
=> CTA visible
```

### Reference есть

```text
currentCps = 23.7
referenceCps = 23.6

=> ratio ≈ 1.004
=> needle visible
=> CTA hidden
```

### Статистики мало

```text
reference exists
comparison sample count low

=> needle visible
=> ratio visible
=> verdict = insufficientConfidence
```

### Статистики достаточно

```text
=> needle visible
=> final verdict visible
```

Это принципиально: **insufficient confidence не должно скрывать измеренное отношение и стрелку**.

# 21. Визуальные правила для устранения всех «неровностей»

Пройти по экрану и унифицировать:

- одинаковые горизонтальные margins;
- одинаковый radius карточек;
- одинаковая высота segmented control;
- одинаковая высота secondary buttons;
- одинаковая baseline заголовков;
- минимум разных font sizes;
- tabular numbers для измерений;
- одинаковые stroke widths;
- одинаковые alpha для secondary text;
- никакого случайного monospace для обычного prose;
- никаких текстов поверх линий графика;
- никаких overlapping labels;
- никакого состояния, где цвет говорит `норма`, а текст говорит `ждём данные`;
- один `SearchGauge` для всех состояний;
- один `ReferenceSummary` после сохранения точки;
- один источник design tokens для spacing/radius/typography.

# 22. Acceptance criteria

Считать исправление завершённым только если выполняются все условия:

1. При поступающих CPS никогда не отображается `Ждём данные прибора`.
2. До reference gauge виден, стрелки нет.
3. После сохранения reference стрелка появляется сразу.
4. При `ratio = 1.0` стрелка отчётливо видна вертикально.
5. Недостаток статистики не скрывает стрелку.
6. `ratio` всегда рассчитывается из current/reference.
7. `Пока недостаточно данных` не является главным заголовком экрана.
8. Большая CTA исчезает после сохранения reference.
9. Все действия reference находятся в компактной строке/overflow.
10. `Отпечаток места` не противоречит собственным накопленным данным.
11. Проверка и Наведение не используют взаимоисключающие статусы одновременно.
12. UI не прыгает при переходах между состояниями.
13. Геометрия gauge одинакова до и после reference.
14. Никакие подписи не пересекаются со стрелкой, дугой и графиком.
15. Все состояния покрыты unit tests.

Главная задача — **не маскировать баг новым текстом**. Сначала исправить модель состояния и источники readiness, затем упростить UI.
