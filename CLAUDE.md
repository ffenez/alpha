# radiacode

Современное Android-приложение для дозиметра-спектрометра RadiaCode 110: подключение по BLE, живые показания, спектр, журнал. Замена официального приложения с упором на приватность и качество UI.

## Stack

- Kotlin, Jetpack Compose (Material 3), coroutines/Flow; minSdk 26
- BLE: Kable (Apache-2.0) + собственный порт протокола cdump/radiacode (MIT, атрибуция обязательна)
- Хранение: Room (SQLite)
- Карта: osmdroid (растровые тайлы OpenStreetMap); геолокация — LocationManager (не Fused)

## Invariants

- Данные измерений и координаты не покидают устройство. Никакой телеметрии, аналитики, крэш-репортинга в сеть. Единственный разрешённый сетевой трафик — анонимная загрузка тайлов карты (с агрессивным кэшем; тайл-запросы не должны содержать ничего, кроме координат тайла).
- Никаких зависимостей от Google Play Services / Firebase — целевое устройство GrapheneOS без GMS.
- BLE-протокол RadiaCode реверс-инжинирен сообществом; собственный код протокола писать по документации/идеям, код копировать только из совместимых по лицензии источников с атрибуцией (GPL-код не копировать).
- Дозиметрические величины: хранить сырые значения и единицы (мкЗв/ч, cps), не терять точность при конвертации.

## Key decisions

- Протокол — чистый Kotlin-порт cdump/radiacode; Open-RadiaCode-Android без лицензии — только идеи, не код (ADR 001)
- Один запрос в полёте, матчинг по эхо заголовка; канонический SPEC_ACCUM = 0x205. Пропуск seq в DATA_BUF не рвёт разбор (записи самоограничены — ресинк, счётчик `seqGaps` в `DataBufResult`, идея qtradiacode); несовпадение эха = хвост прежнего обмена → слить ожидающие ответы и ровно один повтор со свежим seq после 100 мс
- Устройство держит одного BLE-клиента: сосуществование с официальным приложением невозможно, это ограничение UX
- Непрерывное измерение — foreground service + запрос исключения из battery optimization
- UI — дизайн-система «Научный терминал» (вариант F, docs/design/design-language.md): IBM Plex Sans/Mono (OFL, бандлятся), тёмная тема основная + светлая по системе, карточки 14dp/рамка 1dp, каждая величина с погрешностью, оси графиков всегда подписаны; токены в `app/.../ui/theme`, компоненты в `app/.../ui/components`; экраны тонкие, вся тестируемая логика UI — в `ui/logic` (чистый JVM); **поле графика — своя утопленная плоскость** (`chartField` + `chartGrid` в `AppColors`, модификатор `Modifier.chartField()`): до этого график рисовался прямо на карточке и в светлой теме получался белым на белом. Сетка — единый токен на все графики; на полноэкранном добавлены вертикальные линии времени по подписям оси; **движение — токены `ui/theme/Motion.kt`** (150/280/360 мс + 110 мс на уход экрана, кривая standard, ПРУЖИНА `springy()`/`contentSize()` для размеров и «доезжающих» величин, смена экрана и категории настроек — fade through): анимируется СОСТОЯНИЕ ИНТЕРФЕЙСА (смена экрана и категории настроек, раскрытие блоков, цвет статуса и чипов, заполнение индикатора), но НИКОГДА измеренные значения — промежуточные кадры такой анимации показывают числа, которых прибор не измерял; плавно меняется кадр (ось, масштаб, цвет), но не данные внутри него
- Baseline — взвешенная перцентильная полоса P10–P90 по минутным корзинам ПРОФИЛЯ (окно 14 дней, отсечка >3×медианы, активация после 3 ч); отклонение = величина И длительность (`PersistenceTracker`); движок чистый JVM в `app/.../baseline/` (ADR 002). Статистики расширены до P25/P75 + взвешенный MAD = median(|xᵢ − медиана|) БЕЗ коэффициента 1.4826 (он предполагает нормальность, спец §4.1 её запрещает допускать), плюс длительность, число сырых выборок и число корзин (честное n порядковых статистик); `BaselineConfig.ALGORITHM_VERSION`
- **Профили вместо «мест»** (спец §3): `profiles` = имя, иконка, вложенность на ОДИН уровень («Дом / Спальня»; глубже — неоднозначность, чьи это статистики), архив, `autoActivate`, `baselineLearning`, `role` (user/transit/no_place). Правила дерева — чистый `ui/logic/ProfileTree` (нельзя вложить родителя, нельзя заархивировать последний живой профиль, архив родителя забирает детей). Пресеты: Дом, Офис, Дача, Родители, В пути, Без места; последние два по смыслу «ситуация, а не комната» — обучение фона у них выключено
- **Авто-контекст по Wi-Fi БЕЗ разрешения на геолокацию** (спец §3.2): сеть опознаётся локальным хешем адреса шлюза/DHCP из `LinkProperties` (`context/NetworkIdentity`, SHA-256 с доменным префиксом, 16 hex; сырой адрес не хранится). SSID читается ТОЛЬКО как подпись и только если разрешение уже выдано ради карты — сопоставление от него не зависит. Честное ограничение (в KDoc и в UI): одинаковый шлюз `192.168.1.1` у разных сетей даёт одинаковый токен, поэтому привязка = подтверждаемая пользователем подсказка, а не доказательство места. GPS для контекста НЕ используется никогда (единственная подписка на локацию — явная запись трека). State machine чистая: `context/ContextMachine` (`AUTO_KNOWN / AUTO_UNCERTAIN(grace) / AUTO_TRANSIT / NO_CONTEXT / MANUAL`), grace по умолчанию 3 мин (1/2/3/5 в Настройках) отсчитывается от ПОТЕРИ знакомой сети и не перезапускается сменой «нет сети»↔«чужая сеть»; ручной выбор живёт в DataStore и переживает перезапуск сервиса, снимается командой «Вернуться к авто»
- **Baseline admission pipeline** (спец §4.2) — `baseline/BaselineAdmission`, 7 условий В ПОРЯДКЕ спеца, возвращается ПЕРВОЕ невыполненное (иначе пользователю называют симптом вместо причины): обучение профиля, надёжность контекста, свежесть потока (тот же порог 10 с, что в UI), Поиск/эксперимент, карантин, пригодность статистики, ручная заморозка. Сырые данные пишутся ВСЕГДА; вердикт лежит в `samples.baselineExcluded` (ключи — контракт на диске, только дополняются), и только `baselineExcluded IS NULL` кормит baseline. Карантин 30 мин отсчитывается от КОНЦА эпизода отклонения (`QuarantineWindow` двигает дедлайн, пока превышение держится). Условие «статистика пригодна» сознательно слабое (не-конечные/отрицательные значения, нулевой счёт, относительная погрешность >50 %) — строгий критерий по dead-time/pile-up требует замеров на приборе
- **Четыре уровня достоверности** (спец §2) — `ui/logic/Evidence` (MEASURED / CALCULATED / STATISTICALLY_DETECTED / INTERPRETATION), рендер = тишайшая приглушённая мета-подпись рядом со значением (`ui/components/EvidenceTag`). Уровни не смешиваются в одной фразе: доза = изм., доза за сутки = расчёт, статус baseline = стат., колонка «кандидат» в таблице пиков = гипотеза. Сырые измерения на Мониторе метку не носят там, где она была бы шумом
- **«Почему такой вывод»** (спец §17 + `why-conclusion-ui-spec.md`) — шторка с Монитора, собранная как АУДИТОРСКИЙ СЛЕД человеческого вывода: вывод → доказательство → статистика → состояние профиля → критерии алгоритма. Сверху статус с тоном (`WhyTone`: зелёный = внутри исторического диапазона профиля, НЕ «безопасно»; янтарь = неопределённость/недостаток данных; красный = сработал явный критерий; серый = не оценивалось), одна человеческая фраза, пара «Сейчас ↔ Обычно здесь» и мини-шкала P10–P90 с точкой текущего значения (вне диапазона — точка на краю с подписью). Дальше секции: «Сейчас» (доза, счёт с 1σ, свежесть, профиль и как выбран), «Сравнение с профилем» (P10–P90, значение, положение + «около 80 % пригодных исторических измерений… не норматив»), «Статистика профиля» (медиана, P25–P75, MAD с оговоркой «это не погрешность прибора», P10–P90, пригодных данных, минутных корзин), «Состояние статистики» (ОБНОВЛЯЕТСЯ / ВРЕМЕННО НЕ ОБНОВЛЯЕТСЯ / НЕДОСТАТОЧНО ДАННЫХ — слова «обучение/учится/модель» запрещены тестом; исключённое время разбито ПО ПРИЧИНАМ отдельными строками + объяснение, почему отклонение не становится новым baseline), «Как обнаруживается отклонение» (L1, ×P90, минимальная длительность, возврат, окно исключения — числа берутся из `AlarmThresholds` и `BaselineAdmission.QUARANTINE_MILLIS`, один источник истины с движком) и «Спектральное сравнение: пока недоступно» («не оценивалось» ≠ «не обнаружено»). Progressive disclosure: MAD, корзины и пороги свёрнуты за «Показать расчёты», выбор запоминается (`why_calculations_expanded`). Сборка чистая — `ui/logic/WhyReport.kt` (`WhyReportBuilder`), чек-лист §17 спеки живёт тестами `WhyReportTest` (в т.ч. запрет «норма/безопасно/опасно/допустимо» словами, а не подстроками: «не норматив радиационной безопасности» и «нормальное распределение» разрешены)
- **Энергетические окна** (спец §7) — `analysis/EnergyWindows`, по умолчанию 100–300 / 300–700 / 700–1500 кэВ. Границы — ПАРАМЕТР АНАЛИЗА, а не физические категории излучения: редактируются на Спектре, хранятся в DataStore (`energy_windows_kev`, формат `100:300,300:700`), уезжают в отчёт эксперимента. Край окна НЕ дробится: канал целиком относится к окну, если его центр попал внутрь [E₁,E₂) — дробный счёт перестал бы быть пуассоновским (та же причина, по которой `SpectrumMerge` отказывается ребиннить), поэтому вместе с суммой возвращается реально покрытый диапазон. R = C/t, σ_R = √C/t; индекс R_low/R_high = C_low/C_high (общее t сокращается), σ = index·√(1/C_low+1/C_high); индекс — ОПИСАНИЕ СОСТАВА спектра, в UI обязана стоять фраза «не мера опасности»
- **Проекция дозы** (спец §6) — `analysis/DoseProjection`: Ḋ̄ = D_окна / t_ИЗМЕРЕНИЙ (не настенного времени), за год = Ḋ̄ · 8766 ч. Формулировка задана спецификацией и запинена тестом: «если средняя измеренная внешняя фотонная мощность дозы останется такой же — за год ≈ X»; называть это годовой (эффективной) дозой ЗАПРЕЩЕНО, рядом перечислено, что не входит. Меньше часа реальных измерений — проекции нет вовсе
- **A/B эксперимент** (спец §9, §16) — `experiments` + `experiment_runs` (Room v7), экран `ui/screens/AbExperimentScreen` (вход — чип «A/B ▸» со Спектра, навигация самодостаточна). Протокол: сценарий → геометрия описывается ОДИН раз и показывается перед каждым следующим прогоном → прогон A → прогон B → сравнение. Спектр прогона = разность снимков конца и начала (`SpectrumCompare.extractInterval`), сохраняется с `origin='derived'` — такие строки исключены из Истории, из «последнего спектра прибора» и из радонового тренда (иначе короткий интервал попал бы в цепочку накоплений). Математика `analysis/AbAnalysis`: net = G − B·(t_G/t_B), σ_net = √(G + B·(t_G/t_B)²) [IAEA R4, вывод в KDoc]; статистика ПУАССОНОВСКАЯ по счёту: < 25 импульсов в прогоне → отношение правдоподобия (девианс 2[G·ln(G/Ĝ)+B·ln(B/B̂)], Ĝ = (G+B)·t_G/(t_G+t_B)), иначе χ²-подобный z = нетто/σ; считаются обе, использованная названа в результате и в отчёте. Полный спектр — сумма поканальных девиансов/χ² → Wilson–Hilferty, ОДНОСТОРОННИЙ (статистика ниже ν = согласие, а не различие, z зажат снизу нулём). Доза сравнивается как средние с SEM и помечена вспомогательной: секундные показания прибора коррелированы, её неопределённость — оценка снизу. Вердикты ТОЛЬКО `consistent / changed / strong evidence of change` (|z| 2 и 4), «% похожести» запрещён тестом. Старт прогона поднимает `ServiceStatus.experiment` — тот же флаг, что у Поиска; флаг теперь мультиисточниковый (`onExperiment(source, name)`), гаснет только когда снят последним источником, а сервис берёт условие 4 admission-пайплайна прямо из него. Расстояние: серия сравнивается с 1/r² ТОЛЬКО рядом с предупреждением о геометрии/рассеянии/фоне; экранирование: коэффициенты ослабления не выводятся. Экран помечен «экспериментальная функция» до валидации на приборе (спец §24)
- **Воспроизводимость** (спец §22) — `analysis/AlgorithmVersions` единственный источник версий алгоритмов, числа ЗАПИНЕНЫ тестом: смена математики обязана приходить вместе с осознанным бампом версии. Производный снимок несёт `spectra.analysisMeta` (плоский JSON `data/JsonMap`: метод, версии алгоритмов, нормализация, метод фона, источники) — компаратор A−B, объединение, прогоны A/B; эксперимент хранит `algorithmVersion` + `params` (окна, порог переключения статистики, пороги вердикта) и НИКОГДА их не переписывает (старые выводы остаются сравнимыми). Экспорт: RC-XML — метаданные в `SampleInfo/Note`, N42 — в `<Remark>` первыми элементами, эксперимент — текстовый отчёт со всеми прогонами, вердиктами и параметрами. `JsonMap` вместо `org.json` намеренно: колонки читает чистый JVM-код в тестах без Android-заглушки
- **Предагрегация графика (ADR 004, Room v8)** — `minute_stats` (только СКАЛЯРЫ: count, min/max, Σx, Σx², точные МГНОВЕНИЯ экстремумов, first/last, `admittedCount`, профиль; минута со сменой профиля не приписывается никому) + `hour_sketches` (сливаемый KLL-блоб k=128 `algorithmVersion` 1 + точные count/экстремумы с мгновениями). Поминутных скетчей НЕТ сознательно: 60 отсчётов = 240 Б, скетч ≈ 1,3 КБ — дороже самих данных и не точнее. Собственный `analysis/quantiles/KllSketch` вместо Apache DataSketches: лишний вес APK ради одной структуры и глобальный ГПСЧ против требования воспроизводимости (§22) — монета уплотнения берётся из SplitMix64, засеянного КОММУТАТИВНОЙ суммой хешей самих значений, поэтому одни и те же данные дают побайтово одинаковый блоб, а round-trip через блоб — тождество. Измерено: ошибка ранга 0,69 % (час), 1,23 % (100k), **0,29 % на слиянии 720 часов**; хранение ≈ 172 КиБ/сут (≈ 5,1 МиБ/мес против ~5 МБ/сут сырых); слияние месяца 10 мс — поэтому посуточного уровня НЕТ. Колонка длинного пути обязана быть ЦЕЛЫМ числом часов (§28: нельзя приписать колонке распределение часа, который она не покрывает целиком) — сутки это 24 часовые колонки, а не 200; «100–250 корзин» §3 это UX-ориентир, §28 — запрет. Писатель ОДИН (`data/preagg/PreAggregator`, старт одной строкой из `MeasurementService`), всё ПЕРЕСЧИТЫВАЕТСЯ из сырых, а не инкрементируется → идемпотентность, безопасность перезапуска (счётчика нет — нечего удваивать) и самовосстановление, когда прибор отдаёт буфер после переподключения (последние 3 минуты переписываются каждый тик, час с разошедшимся `count` перестраивается); backfill истории — по часам, резюме в самих строках, отмена между часами, прогресс в UI. Экстремумы колонки на длинном окне — ТОЧНЫЕ МГНОВЕНИЯ, поэтому пятисекундный всплеск остаётся помеченным и открываемым по тапу на 30 днях (§21, тест). Оценка по средним под-корзин осталась ТОЛЬКО как fallback на время backfill и в UI названа отдельными словами — у неё нет доказанной границы ошибки. - **Накопленная карта следа («все записи»)** — переключатель на Карте (`MapTrackScope` в DataStore, ключ `map_track_scope`; дефолт без выбора = «все записи», если хоть одна запись есть, иначе «эта запись» с обучающим пустым состоянием). Теперь «все записи» агрегирует ВСЕ `track_points` ДВУМЯ ограниченными SQL-запросами на видимую область (`TrackGridSql`, вынесен в константу, чтобы JVM-тест гонял ИМЕННО его на sqlite-jdbc): (1) точный агрегат области — count/min/max/период по ПОЛНОМУ совпадающему множеству, из него живут все числа сводки; (2) `GROUP BY (клетка, корзина значения)` — гистограмма, размер которой ограничен клетками × 32 корзины, а не числом точек. Порядковые статистики (медиана, P10–P90) считаются по этой гистограмме с точностью корзины, поэтому клетка красится МЕДИАНОЙ, а не средним (один горячий фикс не должен перекрашивать квартал); n, экстремумы и временной охват клетки — точные. Размер клетки следует зуму по лестнице 1/2/5·10ᵏ (≈34 dp на экране), шаг долготы берётся на центральной широте. Ключ клетки: `CAST((lat + 90)/шаг AS INTEGER)` — сдвиг в положительную область обязателен, потому что CAST усекает К НУЛЮ, а `floor()` в SQLite появился в 3.35 (API 31) при minSdk 26; чистые `TrackGrid.latKey/lonKey` повторяют это ровно, и тест на реальном SQLite сверяет обе стороны. Фиксы точнее 50 м (тот же порог, что у длины маршрута) — остальные исключены из ОБОИХ запросов, сводка об этом говорит. Запрос дебаунсится 250 мс по осевшей камере и идёт на IO; если крышка строк когда-нибудь срежет гистограмму, экран честно скажет «картинка построена по N точкам». Тап по клетке даёт медиану, P10–P90, мин/макс, n и период записей в ней.

- **Поиск переизобретён как инструмент локализации** (редизайн `RADIACODE_SEARCH_REDESIGN.md`; ядро — `analysis/RateComparison.kt`, `ui/logic/SearchLadder.kt`, `SearchEngine.kt`, `SearchVerdict.kt`, записка `docs/analysis/search-statistics.md`). Цепочка: показание → **окно решения 3 с** (счёт восстанавливается как N ≈ Σ rᵢ·Δtᵢ по ВРЕМЕНИ ПРИБОРА, дыра укорачивает экспозицию и уходит в `gapSeconds`) → **точный тест двух интенсивностей** (условный биномиальный Przyborowski–Wilenski + интервал Клоппера–Пирсона, перенесённый на отношение скоростей; наивный `z = (тек − фон)/√тек` ЗАПРЕЩЁН и расхождение с ним запинено тестом) → **лестница состояний** (α = 0,01 И выдержка 4 с; снятие 3 с; короткий всплеск = МАРКЕР, не находка) → **направление** Theil–Sen по 10 с. Предпосылка проверяется, а не предполагается: фактор Фано НЕПОДВИЖНОГО окна (записанного фона) — сверхдисперсия правит счёт на φ, недодисперсия НЕ правит в обратную сторону (сглаженный поток несёт меньше информации, а не больше). Окна перекрываются, поэтому тесты коррелированы: 4 с — требование ВЫДЕРЖКИ, а не множитель независимости (αⁿ говорить нельзя). Вся цепочка — чистая функция от показаний и их моментов, поэтому частота перерисовки UI не меняет вывод (§14 редизайна, запинено `SearchEngineTest`). - **Жёсткость** (`analysis/Hardness.kt`) — **документированный коэффициент вендора**: руководство RadiaCode определяет её как безразмерный **(мкрем/ч)/(имп/с)** и говорит, что она позволяет следить за изменением СПЕКТРАЛЬНОГО ХАРАКТЕРА, убрав составляющую интенсивности (нужна прошивка ≥3.0, у RadiaCode Zero не считается). Что это НЕ: **не средняя энергия фотона и не средняя энергия, поглощённая кристаллом** — числитель это дозиметрическая оценка, полученная через энергетическую характеристику прибора, поэтому «средняя энергия: 0,52» на экране ЗАПРЕЩЕНА и запинена тестом. Зачем нужна: подавляет влияние общей интенсивности (то же поле в k раз ярче → обе величины ×k, отношение прежнее), но «ортогональной» её называть нельзя — мешают шум, энергетическая характеристика детектора и погрешность оценки дозы. σ считается по правилу частного, дозовый член — из СОБСТВЕННОЙ погрешности прибора; доза и счёт формируются из одних и тех же событий, а ковариация алгоритмов прошивки НЕ ОПУБЛИКОВАНА, поэтому σ — оценка, а НЕ гарантированная граница (называть её консервативной нельзя: знак поправки неизвестен). Считается из тех же двух чисел, что прибор шлёт по BLE (жёсткости в протоколе нет), спектры не нужны. Величина ПРОИЗВОДНАЯ — в детекторе отпечатка (ADR 005) собственного голоса не имеет
- **Лестница окон графика** — 15 ступеней вместо шести: 1м 2м 3м 5м 10м 30м · 1ч 2ч 3ч 6ч 12ч · 1д 2д 7д 30д (шаг 1-2-3-5-10-30 внутри каждой единицы времени — знакомый шаг циферблата). Ряд длиннее экрана, поэтому лента чипов ПРОКРУЧИВАЕТСЯ и сама подводит выбранный чип (`ChartWindows.scrollTargetIndex`); прежнее «скользящее окно из четырёх чипов» удалено — оно заставляло угадывать соседние ступени. Ниже минуты не идём: прибор пишет раз в секунду. **Лестница СЛЕДУЕТ ЗА ОКНОМ, а не наоборот**: щипок меняет окно плавно, и подсвеченный чип обязан говорить правду — ближайшая ступень ищется по ОТНОШЕНИЮ длительностей (между 1м и 2м столько же «расстояния», сколько между 1ч и 2ч), при точном совпадении (допуск 2 %) чип выбран, между ступенями он просто ярче: «вы примерно здесь», но окно не равно ступени. Щипок не выводит окно за предел, который величина умеет показать честно. Лента **СВЁРНУТА** в один чип с текущим окном («6ч ▾») и разворачивается по нажатию, пряча себя сразу после выбора: пятнадцать чипов на экране постоянно съедали место и требовали прокрутки ради одного нажатия. Между ступенями свёрнутый чип называет ФАКТИЧЕСКОЕ окно («47 мин»), а не ближайшую ступень. Выбранное окно ЗАПОМИНАЕТСЯ по величине (`chart_spans` в DataStore): экран открывается там, где его закрыли. Длительность эпизода никогда не печатается как «0 с» — короче секунды это «<1 с», иначе на графике это читается как «ничего не было». Маркеры экстремумов (▲) объясняются подписью прямо под графиком и только когда они есть
- **Фон графика несёт данные** (`ui/logic/ChartBackground.kt`): **штриховка пропусков** («прибор молчал» и «уровень был низкий» на пустом поле неразличимы — самая опасная двусмысленность на графике измерений; порог показа — сотая доля окна, чтобы фон был одинаково спокоен на любом масштабе), **затенение области до начала истории** («сюда данные не доходят» ≠ измеренный ноль), **зебра времени** (часы или сутки, только на окнах ≥6 ч и не больше 40 полос; привязана к СТЕННЫМ часам, поэтому не дёргается при прокрутке). Всё чистая арифметика по корзинам, рисование ничего не решает
- **Полноэкранный график — один на три величины** (`ui/logic/ChartMetric.kt`): тап по карточке дозы, счёта или жёсткости открывает ОДИН И ТОТ ЖЕ экран с теми же жестами, конвертами, курсором, гистограммой и правилами честности; различаются только колонка данных, единицы и доступные окна. Для счёта и жёсткости добавлены SQL-агрегаты той же формы (`countRateBucketRange`, `hardnessBucketRange`), поэтому вся механика работает без единой ветки в модели ряда. **Жёсткость считается ПО КАЖДОМУ ОТСЧЁТУ** (`MIN/MAX/SUM(doseRate/countRate)` в самом запросе, отсчёты ниже `Hardness.MIN_COUNT_RATE` отброшены): среднее отношений и отношение средних — разные числа, и второе нельзя выдавать за первое. Окна: у дозы все (предагрегация ADR 004), у счёта и жёсткости — только точный путь (≤6 ч), и ПОЧЕМУ их нет, написано словами под графиком. Порог L1 и полоса профиля рисуются только на дозе — они заданы в дозовых единицах. Типы модели ряда переименованы под три величины: `DoseAggregate→ValueAggregate`, `DoseSnapshot→ChartSnapshot`, `DoseChartModel→ChartSeriesModel`
- **Robust autoscale оси значений (`4.md`)** — кадр строится по УСТОЙЧИВЫМ границам колонок (`DoseScales.of`: 2-й процентиль их Q10 снизу, 98-й процентиль Q90 сверху, поля 15 %, минимальный размах `ChartMetrics.minAxisSpan` и доля 15 % от центра, ниже нуля не опускается). Прежняя ось была ЖЁСТКО НУЛЕВОЙ (`LinearDoseScale.minValue = 0`), и самый частый случай выглядел так: фон 0,14–0,18 мкЗв/ч на оси 0…0,30 занимал шестую часть высоты. Буквальные min/max тоже не годятся — один всплеск сжал бы весь ряд, поэтому берутся порядковые статистики, а выброс несут маркер и карточка курсора. **Порог L1 и полоса профиля растягивают кадр, только если они РЯДОМ с данными** (в пределах половины размаха): далёкий L1 = 0,30 при фоне 0,15 удваивал ось; вместо линии рисуется закреплённый указатель «↑ L1 0,30» у верхней кромки — и симметрично «↓ L1» у нижней, когда кадр целиком выше порога. Заодно исправлено: полоса профиля (дозовые P10–P90) больше не рисуется на графиках счёта и жёсткости — там она была числами из другой величины
- **Маркер ▲ — сравнение, а не вердикт об аномалии** (`markerWording`): было «▲ экстремум выше исторического P90 профиля», стало «▲ максимум интервала выше P90 профиля» + строка с обоими числами («макс 0,18 · P90 профиля 0,17»). P90 это девятый дециль исторического распределения — выше него по определению лежит около 10 % пригодных исторических измерений, и превышение P90 само по себе не делает значение статистически исключительным (тем более при n = 2 в интервале). Слово «экстремум» осталось математическим названием min/max внутри интервала и запрещено тестом как классификация аномальности
- **Панель графика: одно правило подсветки и «сейчас» в шапке** — подсвечен чип = НАЗВАННОЕ СОСТОЯНИЕ ВКЛЮЧЕНО. «⌖ сейчас» горел ровно наоборот (когда график НЕ следил за живым краем) и уехал в правый верхний угол, к «i»; шкала стала постоянным «лог» вместо переключающейся надписи «лин/лог» — при меняющемся названии подсветка не значила ничего. **Тап по маркеру ▲ открывает карточку курсора** на этом интервале (порог попадания — 24 dp, полоса над полем): маркер указывает «здесь что-то было», и по нему обязано открываться то же, что по любому месту графика
- **Справка графика — под кнопкой «i», а не полосой под полем** (`ui/logic/ChartInfo.kt`): длинная строка «линия — медиана корзины · Q25–Q75 …» объясняла правильно, но занимала место постоянно и читалась один раз. Теперь в шапке (портрет и ландшафт) есть «i», а под ней — панель ПОВЕРХ экрана с разделами «Что нарисовано / С чем сравнивается / Откуда числа / Жесты»; состав зависит от того, что реально на экране (нет полосы профиля — так и сказано, нет маркеров — про ▲ не пишется, метод квантилей называется тот, которым посчитано ЭТО окно). «Назад» закрывает справку, а не график. Постоянные оговорки самой ВЕЛИЧИНЫ (CPS — не мера опасности, что такое жёсткость) остались под карточкой Главной — `ChartMetrics.footnotes`, прежняя `anatomy()` удалена
- **Машинной отметки метода на графике нет вовсе** (`QuantileMetadata.stamp` удалён): под расширенной статистикой печаталась строка `{"method":…}` — JSON воспроизводимости §22, которому здесь нечего воспроизводить. Числа графика никуда не экспортируются (их смотрят на экране), версия алгоритма уезжает в отладочный отчёт вместе со всеми остальными (`AlgorithmVersions.all`), а метод назван словами строкой выше (`QuantileMetadata.label`: метод, k, версия, ошибка ранга). Промежуточный вариант «скопировать отметку» тоже убран — он сохранял на экране кнопку ради данных, которые некуда приложить

- **ТЗ полноэкранного графика** (`RADIACODE_FULLSCREEN_DOSE_CHART_SPEC.md`) — реализовано: §2 неполное окно называется словами («данных: 47 мин из 6 ч», порог покрытия 95 % — пара процентов пропусков BLE не «неполное окно»); §3 далёкий L1 НЕ растягивает ось (правило `ChartMapping.yMax` было), а когда он выше кадра — закреплённый указатель «↑ L1 0,30» у верхней кромки вместо исчезнувшей линии; §6 распределение стало сворачиваемым блоком; §10 двойной тап = выбранное окно у живого края (отмена зума и панорамы). Тренд ОПИСАТЕЛЬНЫЙ: ни значимости, ни доверительного интервала (1 Гц поток автокоррелирован, интервал по τ Кендалла был бы в разы уже правды). Гистограмма окна — Freedman–Diaconis h = 2·IQR·n^(−1/3) с клампом [8, 40] и округлением границ (кламп — ПРОДУКТОВАЯ эвристика, §14 прямо это говорит) и тремя обязательными fallback'ами: IQR = 0 → правило √n, наблюдений <20 → «недостаточно данных для распределения» вместо картинки, все значения равны → одна корзина; n в FD — число под-корзин (честное n порядковых статистик), ось Y подписана тем, что реально считает: «секунд измерений (1 Гц)»

(3) Числа агрегации (интервалы, записи, шаг, число полос, покрытие окна) уехали из-под картинки в карточку «i»
