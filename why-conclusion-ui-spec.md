# Спецификация меню «Почему такой вывод»

## 1. Назначение

Меню «Почему такой вывод» — не справка и не экран для обычного ежедневного просмотра. Оно должно отвечать на один вопрос:

**Почему приложение прямо сейчас показывает именно такой статус?**

Экран должен одновременно:
- дать понятный ответ за 2–3 секунды;
- позволить проверить вывод по исходным измерениям и статистике профиля;
- чётко отделять измеренное прибором от вычисленного приложением и статистического вывода;
- не использовать слова «норма», «безопасно» или «допустимо» там, где речь идёт только об историческом диапазоне конкретного профиля;
- не скрывать неопределённость, недостаток данных или исключение данных из статистики.

Главный принцип:

**Вывод → непосредственное доказательство → статистическая основа → состояние профиля → критерии алгоритма.**

Не начинать экран с MAD, количества корзин, карантина или внутренних условий алгоритма.

---

## 2. Верхний блок: ответ пользователю

Вверху:

### Почему такой вывод

Затем крупно текущий вывод, например:

**В обычном диапазоне этого профиля**

Под ним одна человеческая фраза:

> Текущая мощность дозы находится внутри исторического диапазона P10–P90 профиля «Дом».

Далее компактное визуальное доказательство:

**Сейчас**  
`0,16 мкЗв/ч`

**Обычно здесь**  
`0,14–0,17 мкЗв/ч`

Желательно показать горизонтальную мини-шкалу P10—P90 с точкой текущего значения. Это быстрее читается, чем ещё одна строка текста.

Важно: «обычно» означает только исторически наблюдавшийся диапазон этого профиля. Это не норматив безопасности.

---

## 3. Данные прямо сейчас

Следующий блок — только измерения, необходимые для проверки текущего состояния.

### Сейчас

- **Мощность дозы:** `0,16 мкЗв/ч` · `изм.`
- **Скорость счёта:** `25,3 ± 5,0 с⁻¹` · `изм.`
- **Данные:** `обновлены только что` · `изм.`
- **Профиль:** `Дом` · `авто`
- Подпись: `выбран автоматически по знакомой Wi‑Fi сети`

Для CPS можно оставить раскрываемую техническую подпись:

`1σ Пуассона ≈ √(N/τ), τ = 1 с`

Не превращать CPS в дозу самостоятельно. Использовать мощность дозы, которую предоставляет прибор/поддерживаемый протокол.

---

## 4. Почему статус именно такой

Этот блок должен быть самым понятным после верхнего ответа.

### Сравнение с профилем

- **P10–P90:** `0,14–0,17 мкЗв/ч` · `стат.`
- **Текущее значение:** `0,16 мкЗв/ч` · `изм.`
- **Положение:** `внутри P10–P90` · `расчёт`

Пояснение:

> P10–P90 — диапазон, внутри которого находилось около 80% пригодных исторических измерений этого профиля. Это характеристика данного места, а не норматив радиационной безопасности.

Никаких формулировок вида:
- «радиация безопасна»;
- «уровень нормальный»;
- «допустимое значение».

---

## 5. Статистическая основа

Этот блок нужен для проверяемости вывода, но визуально должен быть ниже непосредственного доказательства.

### Статистика профиля

- **Медиана:** `0,15 мкЗв/ч`
- **P25–P75:** `0,15–0,16 мкЗв/ч`
- **MAD:** `0,01 мкЗв/ч`
- **P10–P90:** `0,14–0,17 мкЗв/ч`
- **Пригодных данных:** `23 ч`
- **Минутных корзин:** `1441`

Под MAD:

> Медиана |xᵢ − median(x)| — робастная характеристика наблюдаемого разброса, не требующая предположения о нормальном распределении.

Не подписывать MAD как «погрешность прибора».

Если показывается SD, писать полностью:

`SD 0,01 мкЗв/ч · наблюдаемый разброс`

Не использовать голое `σ 0,01`, чтобы его нельзя было принять за неопределённость измерительного прибора.

---

## 6. Состояние статистики профиля

Не использовать слова «обучение», «учится» или «модель обучается». Здесь нет необходимости создавать впечатление ML.

### Статистика профиля

Состояния:

**Обновляется**  
Новые пригодные измерения учитываются при пересчёте исторического диапазона.

**Временно не обновляется**  
Новые измерения сохраняются, но временно не используются для обновления исторического диапазона.

**Недостаточно данных**  
Например: `2 ч 14 мин из минимально необходимых 3 ч`.

Если данные исключаются:

**Не учтено в статистике:** `8,7 ч`

Причины отдельными строками:
- режим «Поиск» / эксперимент: `8,0 ч`;
- период после отклонения: `44 мин`;
- неизвестный контекст;
- потеря связи;
- другие реально реализованные критерии допуска.

Не писать просто «карантин после отклонения» без объяснения.

Пользовательская формулировка:

> После устойчивого отклонения новые измерения некоторое время сохраняются, но не добавляются в обычный диапазон профиля. Это предотвращает постепенное превращение самого отклонения в новый baseline.

Техническое слово `quarantine` допустимо только в раскрываемых деталях/режиме разработчика.

---

## 7. Длительное изменение обстановки

Нельзя автоматически считать длительно повышенный уровень новым обычным уровнем только потому, что он держится долго.

Если отклонение сохраняется достаточно долго, приложение может предложить:

### Уровень изменился надолго

> Показания устойчиво отличаются от исторического диапазона профиля «Дом». Возможно, изменилось место прибора или сама обстановка.

Кнопки:

**Обновить профиль**  
**Оставить как есть**

При обновлении:
- старый baseline сохранить в истории;
- новый период начать отдельно;
- действие пользователя зафиксировать;
- не переписывать прошлые сырые измерения.

Автоматически принимать новый baseline без подтверждения пользователя нельзя.

Конкретную длительность, после которой появляется предложение, не считать физической константой. Она должна быть параметром продукта и пройти полевую валидацию.

---

## 8. Критерии обнаружения

Это технический блок. По умолчанию он может быть свёрнут:

### Как обнаруживается отклонение ▾

Внутри показывать **реально реализованный алгоритм**, а не пример из документации.

Например:

- абсолютный порог L1: `0,30 мкЗв/ч`;
- относительный критерий: `2 × P90 профиля`;
- минимальная длительность: `2 мин`;
- условия возврата;
- период исключения после события.

Но эти значения нельзя представлять как научно универсальные границы опасности. Это параметры алгоритма обнаружения события.

Критически важно: в проекте должен существовать один источник истины для этих параметров. UI, документация и код не должны описывать разные критерии.

---

## 9. Спектральная часть

Если спектральное сравнение ещё не реализовано:

**Спектральное сравнение:** `пока недоступно`

Пояснение:

> Текущий вывод основан на мощности дозы, скорости счёта и статистике профиля. Спектр в этот вывод сейчас не входит.

Не писать «спектральной аномалии нет», если алгоритм её фактически не оценивал.

После реализации различать:

- `не обнаружена`;
- `обнаружено изменение`;
- `недостаточно статистики`;
- `не оценивалось`.

Это принципиально разные состояния.

---

## 10. Маркировка происхождения данных

Сохранить идею:

- `изм.` — значение получено от прибора;
- `расчёт` — арифметически вычислено из измерений;
- `стат.` — результат статистической обработки исторических данных.

Внизу экрана можно оставить легенду:

> **изм.** — измерено прибором · **расчёт** — вычислено из измерений · **стат.** — результат статистической модели профиля

Лучше использовать «статистическая модель профиля», а не «обученная модель».

---

## 11. Progressive disclosure

Меню должно иметь два информационных уровня без перехода на отдельный экран.

### Сразу видно

1. вывод;
2. текущее значение;
3. обычный диапазон места;
4. почему значение соответствует/не соответствует ему;
5. свежесть данных;
6. активный профиль.

Этого достаточно большинству пользователей.

### «Показать расчёты»

Раскрывает:
- медиану;
- P25–P75;
- MAD;
- N;
- длительность накопления;
- исключённые данные;
- причины исключения;
- алгоритмические пороги;
- технические формулы;
- состояние спектрального анализа.

Приложение запоминает выбор пользователя. Если человек постоянно раскрывает расчёты, можно оставлять их раскрытыми.

---

## 12. Минимум действий

Пользователь не должен вручную:
- выбирать профиль каждый раз при приходе домой;
- запускать сбор baseline;
- подтверждать обычные измерения;
- очищать карантин;
- решать, какие точки статистически пригодны;
- запускать пересчёт;
- выбирать между P10/P90, MAD и другими методами.

Профиль определяется автоматически по настроенному контексту, в первую очередь по знакомой Wi‑Fi сети.

Если контекст неизвестен:

**Вне профиля**

Измерения продолжают сохраняться, но не должны автоматически загрязнять baseline известного места.

Ручной выбор профиля — override, а не основной сценарий.

---

## 13. Визуальная структура

Рекомендуемый порядок элементов:

1. `Почему такой вывод`
2. крупный статус
3. одна строка объяснения
4. `Сейчас ↔ обычно здесь`
5. мини-шкала положения текущего значения в P10–P90
6. блок «Сейчас»
7. блок «Статистика профиля»
8. блок «Состояние статистики»
9. `Показать расчёты`
10. технические критерии
11. легенда происхождения данных
12. `Понятно`

Не делать все строки одинаково визуально значимыми.

Иерархия:
- вывод — самый заметный;
- доказательство — второе;
- числа статистики — третье;
- внутренние механизмы — четвёртое.

---

## 14. Цвет

Цвет должен кодировать состояние, а не создавать медицинский/санитарный вывод.

Например:
- зелёный — значение соответствует историческому диапазону профиля;
- янтарный — статистическая неопределённость, недостаток данных, временное исключение, необычное изменение;
- красный — сработал явно заданный alarm/критерий события;
- серый — неизвестно / не оценивалось / нет данных.

Зелёный **не означает «безопасно»**.

## 16. Научные ограничения интерфейса

UI никогда не должен утверждать больше, чем позволяют данные.

Обязательные различия:

`внутри исторического диапазона профиля`
≠
`безопасно`

`выше P90`
≠
`опасно`

`статистически необычно`
≠
`радиоактивный источник обнаружен`

`спектральный кандидат`
≠
`радионуклид идентифицирован`

`не оценивалось`
≠
`не обнаружено`

`CPS вырос`
≠
`доза выросла пропорционально`

Все выводы должны быть воспроизводимы из сохранённых исходных данных и задокументированного алгоритма.

---

## 17. Проверка перед реализацией

Перед выпуском этого меню проверить:

- [ ] статус выводится из тех же условий, которые показаны в «Почему?»;
- [ ] UI и код используют одни и те же пороги;
- [ ] P10–P90 подписан как исторический диапазон профиля, а не норматив;
- [ ] MAD не называется погрешностью;
- [ ] SD не обозначается двусмысленным голым σ;
- [ ] CPS не используется как самостоятельная мера опасности;
- [ ] «не оценивалось» не превращается в «не обнаружено»;
- [ ] исключённые из baseline данные не удаляются из сырой истории;
- [ ] изменение масштаба графиков не меняет статистический вывод;
- [ ] длительное отклонение не становится baseline автоматически;
- [ ] неизвестный профиль не загрязняет статистику известного профиля;
- [ ] пользователь может понять причину статуса без раскрытия технического блока;
- [ ] исследователь может раскрыть все числа, необходимые для проверки вывода.

## 18. Главный продуктовый принцип

Меню «Почему такой вывод» должно быть не «экраном со всей статистикой», а **аудиторским следом человеческого вывода**.

Пользователь сначала видит:

**что произошло → с чем сравнили → почему получился такой вывод.**

И только затем, если ему это интересно:

**какими статистиками → на каком объёме данных → при каких критериях → какие данные были исключены.**

Так интерфейс остаётся простым для обычного владельца RadiaCode, но не теряет исследовательскую и научную проверяемость.
