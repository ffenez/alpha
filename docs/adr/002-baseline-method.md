# 002. Personal baseline: взвешенная перцентильная полоса P10–P90 с отсечкой всплесков

Дата: 2026-08-09. Статус: accepted

## Контекст

SPEC требует персональный baseline по местам: приложение постепенно понимает «обычный фон» (typical dose rate 0.09–0.14 µSv/h, typical CPS 18–27) и формулирует статус относительно него, а не только по абсолютному порогу. Жёсткие требования: baseline активируется только после достаточной продолжительности измерений; случайный короткий всплеск не должен становиться новой нормой; статус отклонения требует одновременно величины И длительности превышения. Расчёт должен быть статистически честным (Baseline comparison — отдельная категория данных, SPEC «Научная корректность») и дёшевым на телефоне при месяцах данных.

## Решение

Чистый JVM-модуль `app/.../baseline/` (без Android-зависимостей, полностью покрыт юнит-тестами).

- **Вход**: минутные агрегаты 1 Гц сэмплов места (AVG dose rate, AVG CPS, число секунд) из Room за скользящее окно 14 дней. Агрегация в SQL — на телефоне это один индексированный range-scan.
- **Отсечка всплесков**: считается взвешенная (по секундам) медиана мощности дозы; корзины с дозой > 3×медианы считаются периодами отклонения и исключаются целиком (и для дозы, и для CPS). Всплеск не входит в статистику вообще.
- **Активация**: суммарное время оставшихся корзин ≥ 3 ч, иначе состояние Learning («изучаю обычный фон — N ч из M»). Исключённое время всплесков в активацию не засчитывается.
- **Полоса**: взвешенные nearest-rank перцентили P10/P50/P90 дозы и CPS по оставшимся корзинам. Без интерполяции — честная порядковая статистика.
- **Защита от «всплеск стал нормой» двойная**: отсечка убирает грубые выбросы, а перцентили — порядковые статистики: остаточное превышение сдвигает P90 только когда занимает >10 % накопленного времени (≥ ~18 мин при минимальных 3 ч). Это требование «прожитого времени», а не дрейф среднего. Устойчиво новый уровень (например, переезд прибора) в полосу со временем входит — отвергаются только транзиенты.
- **Отклонение = величина И длительность**: величина — `dose ≥ L1` ИЛИ `dose ≥ relFactor × P90` (пороги из настроек тревог Simple/Custom); длительность — `PersistenceTracker` (rising-edge, толерантность к провалам ≤ 15 с, срабатывание ровно один раз за превышение). «Выше обычного» — более мягкое условие (>1.05×P90, ≥ 60 с); «Уровень радиации изменился» — подтверждённое стойкое отклонение, пишется в журнал событий.

## Альтернативы

- **Среднее ± kσ** — не робастно: один всплеск утаскивает и среднее, и σ; отклонено.
- **EMA/скользящее среднее с медленной постоянной** — всплеск всё равно постепенно втекает в норму, скорость втекания скрыта от пользователя; отклонено.
- **MAD (median absolute deviation)** — робастно, но полоса «медиана ± k·MAD» предполагает симметрию, а фон асимметричен (хвост вверх); перцентили выражают «обычный диапазон» напрямую и понятнее объясняются в UI.
- **Отдельная таблица инкрементальной статистики** (t-digest и т.п.) — экономит CPU, но добавляет второй источник правды и код миграций; SQL-агрегация 14 дней (~20 тыс. минутных корзин) укладывается в доли секунды — не нужно.

## Последствия

- Один и тот же движок питает статус Монитора, полосу графика, сводки мест в Настройках и события журнала — формулы не дублируются.
- Baseline пересчитывается заново из сырых данных при каждом запросе — нет скрытого состояния, миграций статистики и расхождений после правок метода.
- Константы (3 ч, P10–P90, 3× отсечка, 14 дней) зафиксированы в `BaselineConfig` и покрыты тестами; калибровка по полевому опыту — правка одного места.
