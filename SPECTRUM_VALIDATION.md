# SPECTRUM_VALIDATION.md

## Задача

Проведи отдельный научно-технический аудит спектрального анализа приложения перед релизом.

Есть подозрение на регрессию между старой и новой реализацией анализа одного и того же типа спектров: отличаются найденные энергии пиков и особенно их статистическая значимость. Нельзя выбирать реализацию по тому, какая визуально выглядит правдоподобнее. Нужно установить причину расхождения на уровне исходных данных, формул и алгоритмов и оставить только доказанно корректное поведение.

## Входные данные

Я предоставлю **исходный спектр RadiaCode в формате XML**.

Считай XML основным входным эталоном. Не извлекай значения со скриншотов, если соответствующие исходные данные доступны в XML.

Официальный XML RadiaCode может содержать:
- spectrum;
- background;
- число каналов;
- время накопления;
- коэффициенты энергетической калибровки;
- сведения об устройстве.

Если background присутствует внутри XML, используй именно его там, где алгоритм требует фон. Если background отсутствует — явно зафиксируй это и не выдумывай его.

Перед анализом:
1. распарсь XML;
2. перечисли реально найденные поля;
3. зафиксируй число каналов;
4. время накопления;
5. calibration coefficients;
6. наличие/отсутствие background;
7. число импульсов;
8. любые другие параметры, реально влияющие на вычисления.

Не полагайся на предполагаемую структуру XML — сначала исследуй фактический файл.

## Главный принцип

Нужна воспроизводимая цепочка:

raw channel counts
→ channel index
→ energy calibration
→ energy, keV
→ background/baseline
→ smoothing
→ peak candidates
→ peak localization
→ peak boundaries/window
→ gross counts
→ background counts
→ net counts/area
→ uncertainty
→ significance
→ isotope/line matching

Для каждого этапа должно быть возможно показать вход, формулу/алгоритм и выход.

Никаких скрытых эвристик, magic numbers или необъяснённых преобразований.

## 1. Найди все реализации спектрального анализа

Пройди по всему репозиторию и найди:

- XML/import parser;
- spectrum storage/model;
- channel → energy conversion;
- calibration;
- interpolation/resampling;
- smoothing/filtering;
- baseline estimation;
- background subtraction;
- peak detection;
- peak localization;
- peak integration;
- peak width/FWHM;
- uncertainty;
- significance / sigma;
- isotope matching;
- expected-line consistency checks;
- UI formatting, которое может изменять или округлять результат.

Найди также старую реализацию через:
- git history;
- удалённые/заменённые функции;
- предыдущие commits;
- legacy code;
- тесты;
- сохранённые алгоритмы.

Если старый код недоступен, не реконструируй его по догадке. Зафиксируй это.

## 2. Один XML — одинаковый вход

Один и тот же XML должен быть прогнан через сравниваемые реализации.

Запрещено сравнивать результаты двух разных физических измерений как доказательство ошибки алгоритма.

Создай детерминированный тестовый fixture из предоставленного XML, чтобы последующие изменения алгоритма можно было проверять на абсолютно одинаковых counts.

Проверь, что ни одна реализация не меняет исходные channel counts при импорте.

## 3. Проверка энергетической калибровки

Определи точную формулу, которую использует приложение.

Если XML содержит коэффициенты калибровки, используй коэффициенты из файла как исходные данные и покажи, как из channel index получается keV.

Для нескольких контрольных каналов выведи:

| channel | raw count | calculated keV |
|---:|---:|---:|

Проверь:
- zero/one-based indexing;
- порядок коэффициентов;
- линейный/квадратичный член;
- Float/Double;
- округление;
- преобразование до или после peak localization;
- использование центра bin;
- интерполяцию между каналами;
- возможное повторное применение calibration;
- использование текущей калибровки прибора вместо калибровки XML.

Особенно расследуй, почему в разных версиях область K-40 могла отображаться примерно как 1429–1441 keV.

Не подгоняй к 1460.8 keV вручную.

## 4. Raw spectrum должен быть неприкосновенным

Создай отдельное представление исходных данных:

channel[i]
count[i]

Raw counts нельзя:
- сглаживать in-place;
- нормализовать in-place;
- заменять интерполированными значениями;
- модифицировать для UI;
- перезаписывать после background subtraction.

Все производные массивы должны быть отдельными.

Добавь тест, подтверждающий неизменность raw counts после полного анализа.

## 5. Сглаживание

Установи:
- какой фильтр используется;
- размер окна;
- параметры;
- применяется ли фильтр к поиску пиков или только отображению;
- влияет ли переключатель UI «сглаживание» на научный результат.

Отображение не должно незаметно менять численный результат анализа, если это не является явно определённой частью алгоритма.

Сравни peak position до и после smoothing.

## 6. Peak detection

Для каждого найденного candidate peak выведи диагностическую таблицу:

| peak | channel | energy | raw counts | smoothed counts | left bound | right bound | FWHM | gross | background | net | uncertainty | significance |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|

Установи:
- как определяется локальный максимум;
- как выбираются границы;
- используется ли FWHM;
- зависит ли ширина окна от энергии;
- как обрабатываются overlapping peaks;
- как исключается continuum;
- как обрабатывается край спектра.

Peak position не должен автоматически означать просто maximum bin, если текущая научная модель предполагает centroid/fit.

## 7. Baseline и background — не одно и то же

Отдельно установи смысл каждого понятия в коде.

Не смешивай:
- физически измеренный background spectrum;
- локальный continuum под пиком;
- математический baseline;
- smoothing;
- background profile пользователя.

Для каждого peak покажи, что именно было вычтено.

Если background имеет другое время накопления, проверь корректность нормализации по live/accumulation time.

## 8. Критический аудит significance / σ

Это приоритетная часть расследования.

Ранее наблюдались очень большие расхождения между версиями, например порядка:

- низкоэнергетический peak: ~43σ против ~180σ;
- область K-40: ~20σ против ~94σ.

Эти числа использовать только как указатель на место возможной регрессии, а не как ground truth.

Найди точную формулу significance.

Покажи её математически.

Для каждого члена формулы укажи:
- физический/статистический смысл;
- единицы;
- источник variance;
- учитывается ли uncertainty background;
- предполагается ли Poisson statistics;
- используются gross или net counts;
- не используется ли ошибочно sqrt(net);
- не теряется ли variance при subtraction;
- не считается ли один и тот же count дважды;
- не делится ли area на слишком маленькую sigma;
- не используется ли сглаженный массив как независимые Poisson counts.

Выполни ручной независимый пересчёт минимум для:
1. сильного низкоэнергетического peak;
2. K-40 candidate;
3. слабого candidate;
4. участка без очевидного peak.

Результат ручного расчёта сравни с приложением.

## 9. Статистическая корректность

Проверь применимость Gaussian/sigma approximation при имеющихся counts.

Для малых counts не выдавай формально красивую sigma, если используемая аппроксимация статистически неприменима.

Если текущая метрика на самом деле не является Gaussian standard deviations, нельзя обозначать её «σ». Либо исправь вычисление, либо название метрики.

Не меняй научную модель только ради совпадения со старой версией.

## 10. Проверка известных гамма-линий

Используй известные линии только как независимую проверку энергетической шкалы и matching, а не как способ насильно сдвинуть найденный peak.

В частности проверь K-40 около 1460.8 keV, если в данном спектре действительно имеется статистически обоснованный peak в соответствующей области.

Если доступны другие достоверные линии в XML, используй несколько линий по диапазону энергий.

Для каждой:
- expected energy;
- measured energy;
- absolute error;
- relative error;
- channel;
- uncertainty/peak width.

По одной линии нельзя автоматически заключать, что вся calibration корректна.

## 11. Isotope matching

Matching должен происходить после корректного определения peak energy и uncertainty.

Проверь:
- tolerance;
- зависимость tolerance от energy resolution;
- FWHM;
- многолинейные нуклиды;
- обязательные/поддерживающие линии;
- contradiction logic;
- false-positive protection.

Не идентифицируй нуклид только потому, что одна линия попала в широкое окно.

Разделяй:
- measured peak;
- candidate line;
- supported isotope;
- confirmed identification.

Приложение не должно создавать ложную уверенность.

## 12. Проверка UI

После установления правильной численной реализации проверь, что UI отображает именно её результат.

Ищи:
- другое округление;
- неправильную locale conversion;
- truncation;
- Int вместо Double;
- stale state/cache;
- повторный пересчёт;
- другой массив данных для fullscreen;
- различия между live spectrum и history spectrum;
- различия при включении Log/Lin/Степень;
- влияние «фон»;
- влияние «сглаживание».

Lin/Log/Степень должны менять визуальное представление оси, а не исходную физическую энергию peak.

## 13. Сравнение реализаций

Сформируй таблицу:

| Stage | old | current | reference calculation | verdict |
|---|---|---|---|---|

Для каждого отличия найди первую точку, где результаты расходятся.

Не сравнивай только конечные UI values.

Например, если:
- raw counts совпадают;
- calibration расходится;

то расследование начинается с calibration.

Если:
- energy совпадает;
- peak bounds расходятся;

то проблема ниже по pipeline.

Если:
- area совпадает;
- significance расходится;

то проблема в uncertainty/statistical model.

## 14. Не считать старую версию эталоном

Старая версия не является ground truth.

Новая версия также не является ground truth.

Ground truth для программной части:
- исходный XML;
- математически определённые преобразования;
- документированные calibration coefficients;
- воспроизводимые статистические расчёты;
- независимые reference calculations;
- физически известные линии как внешний sanity check.

Если обе реализации ошибочны — реализуй третью, корректную.

## 15. Автоматические regression tests

После исправления добавь тесты минимум на:

- XML parsing;
- сохранение raw counts;
- calibration coefficients;
- channel → keV;
- peak position;
- peak bounds;
- background normalization;
- net area;
- uncertainty;
- significance;
- isotope tolerance;
- известные synthetic spectra;
- spectrum без peak;
- слабый peak;
- два близких peak;
- low-count spectrum;
- high-count spectrum;
- один реальный XML fixture.

Для synthetic tests ground truth должен быть известен заранее.

Тесты не должны просто копировать production implementation и тем самым подтверждать саму себя.

## 16. Golden diagnostic report

Добавь debug/test-команду, которая для XML создаёт машиночитаемый отчёт, например:

spectrum_validation.json

В нём должны быть:
- metadata, необходимая для анализа;
- calibration;
- raw spectrum checksum;
- accumulation time;
- background information;
- detected peaks;
- bounds;
- gross/net counts;
- uncertainty;
- significance;
- candidate isotopes;
- причины принятия/отклонения matches.

Не включай в отчёт серийный номер устройства или другие ненужные идентификаторы.

## 17. Privacy

XML RadiaCode может содержать серийный номер прибора и другие metadata.

Для научного расчёта используй только действительно необходимые поля.

Не копируй идентификаторы устройства:
- в fixtures;
- snapshots;
- logs;
- отчёты;
- git;
- release artifacts.

При создании fixture сделай sanitized copy, сохранив counts, calibration, accumulation/background и прочие данные, необходимые для воспроизводимости.

## 18. Что нельзя делать

Запрещено:

- подгонять коэффициенты под ожидаемый K-40;
- менять формулу только потому, что старая версия показывала другое число;
- считать скриншот ground truth;
- использовать UI curve вместо raw channel counts;
- скрывать расхождения округлением;
- оставлять magic constants без происхождения;
- объявлять isotope найденным без статистического основания;
- исправлять только отображение, если ошибка находится в analysis pipeline;
- удалять неудобные тестовые данные;
- молча заменять отсутствующий background синтетическим.

## 19. Итоговый отчёт

Создай `SPECTRUM_VALIDATION_REPORT.md`.

Он должен содержать:

### Исходные данные
Что реально было прочитано из XML.

### Найденные реализации
Какие части old/current pipeline обнаружены.

### Первая точка расхождения
Точное место, где результаты начинают отличаться.

### Root cause
Конкретная причина или причины.

### Математическая проверка
Формулы и независимые контрольные расчёты.

### Calibration
Результаты проверки энергетической шкалы.

### Peaks
Сравнение positions/bounds/areas.

### Significance
Почему получались разные σ и какое вычисление корректно.

### Isotope matching
Какие совпадения действительно поддерживаются данными.

### Исправления
Файлы и функции, которые были изменены.

### Tests
Какие regression/scientific tests добавлены и результаты их запуска.

### Remaining uncertainty
Что невозможно доказать по имеющемуся XML.

Не пиши «исправлено» без доказательства тестом или численным сравнением.

## Критерий завершения

Работа закончена только когда можно взять предоставленный XML на чистом checkout, выполнить один воспроизводимый validation test/command и получить тот же результат анализа с объяснимой цепочкой:

XML raw counts
→ calibration
→ peak
→ area/background
→ uncertainty
→ significance
→ isotope candidate

Если причина расхождения не установлена, прямо напиши, что она не установлена. Не выбирай наиболее правдоподобную версию по предположению.
